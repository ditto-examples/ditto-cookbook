- Update the guide to version 3.2 with findings that lose data or stop sync without an error, observed on SDK 5.1.0 and 5.2.0. Do not copy a persistence directory to another device or delete only part of it: copies never converged with the original, and a device whose `ditto_store` was deleted did not send some new documents. `close()` and `sync.stop()` do not wait for changes that are still being sent, so wait for the write's `commitID` (with a timeout, as a new example shows) where data must reach another device before Ditto closes. - Update the guide to version 3.3 with more findings from SDK 5.1.0 and 5.2.0. On 5.2.0, a merge that would exceed the hard size limit leaves the devices with different versions of the document whose updates stop in both directions, and evicting it on one device discards that device's changes; the guide now states this from testing instead of the release notes. A new section, Reordering on two devices, shows that renumbering every entry discards a concurrent reorder, so a move writes only the moved entry's position, between its new neighbors. The guide also shows that an undeclared `SET` over a counter is undone by the next increment, that renaming a field in place loses what old versions write, that `INSERT ... SELECT` needs `COUNTER` and `ATTACHMENT` declarations on both sides, that a document re-inserted after `EVICT` merges with other devices' copies, that `char_length` counts code points, that the JavaScript SDK changes strings with unpaired surrogates, and that the legacy `PN_COUNTER` accumulates rounding errors. Checklist labels that version 3.1 should have changed now name both releases as well. The `ditto` plugin Skills (1.7.0) and the checklist (2.13) follow.
- Update the guide to version 3.4 with clock, reaping, upgrade, and subscription findings from SDK 5.1.0 and 5.2.0. Clock drift now explains that Ditto's last-writer-wins follows device clocks: a device 5 seconds fast won over a write made 2 seconds later, and every device that synced with a device whose clock was ahead wrote later timestamps too, without a warning. Tombstone TTL and reaping now describes zombie data as observed, a TTL that follows the deletion's timestamp, when reaping runs (a random time within 10 minutes of the first start, so apps that run briefly reap rarely), and `REAPER_PREFERRED_HOUR` as a local hour that a device must be running in. Devices on 5.0.x should upgrade directly to 5.2.0: a store migrated by 5.1.0 kept failing writes to a collection whose index was created while empty, until the index was dropped and created again. The 5.1.0 issue of stalling observers now gives the threshold we observed (about 60). Subscriptions follow the rules of local queries (`!=` and `NOT IN` drop documents without the field), and they are not persisted, so register them after every `Ditto.open()`. Checklist labels that version 3.1 missed now name both releases as well. The `ditto` plugin Skills (1.8.0) and the checklist (2.14) follow.
- Update the guide to version 3.5 with connection, relay, test, and platform findings from SDK 5.1.0 and 5.2.0. Each device sends its changes over one connection to a peer, so a connection that stalls without closing holds up sync until it is dropped (about 7 seconds for TCP and 15 for WebSocket), even when another transport works. `clock()` in a subscription is evaluated by each sending device with its own clock, only when a document is written or a new subscription arrives, and an observer with `clock()` does not update as time passes. A receiver also connected to the writer can show orders without their items for up to about 0.7 seconds when a relay that subscribes only to orders is its faster path. Groups of test peers need their own port and Database ID (`openSyncedPeers` takes a `databaseID`), environment variables for system parameters are read as JSON and ignored with only a log line when invalid, the JavaScript SDK stores a `Date` as `{}` and `undefined` as `null`, and on 5.2.0 observer rows of a query without `_id` carry no `_id`, so `Differ` needs it projected. The `ditto` plugin Skills (1.9.0) and the checklist (2.15) follow.
- Update the guide to version 3.6 with storage, logging, and hub findings from SDK 5.1.0 and 5.2.0. `DELETE` and `EVICT` leave most values readable in the database files, so a store that must be wiped is closed and its directory deleted, and the guide now gives that procedure for Flutter and JavaScript, including what happens when the directory is deleted while Ditto is open. The on-disk logs contain the text and arguments of a device's subscriptions and of those of directly connected devices, so subscriptions are not filtered by personal data. On 5.2.0, a device counts the connections it opened itself when it decides whether to accept another one, outgoing connections are not limited, and the at-capacity settings keep replacing connections; a new paragraph estimates the CPU and memory a hub spends per connected client. The `ditto` plugin Skills (1.10.0) and the checklist (2.16) follow.
- Update the guide to version 3.7 with findings about many devices, subscriptions, and attachments from SDK 5.1.0 and 5.2.0. When many devices reconnect at once with offline changes and every device subscribes to everything, the time until all devices agree grows faster than their number, so scoped subscriptions matter most there; staggered starts spread the hub's work but do not reduce it. Each new subscription makes the serving peer read the whole collection for all of the device's subscriptions, whatever its indexes, so the long-lived set is registered together, before `ditto.sync.start()` where possible. In a mesh where every device connects to every other, each device received each new document 3 to 5 times, so Key Characteristics no longer says that peers exchange only what the other side has not seen. A fetch of an attachment whose document was deleted stayed pending on 5.2.0 as well, contrary to the 5.2.0 release notes, so the Known Issues and Fetching Attachments sections now say so; unreferenced blobs were collected within about 10 minutes, and a deleted document's blob could still be fetched from a peer that had not collected it yet. The `ditto` plugin Skills (1.11.0) and the checklist (2.17) follow.
- Update the guide to version 3.8 with findings about slow links, document weight, and observers from SDK 5.1.0 and 5.2.0. An attachment transfer delays other changes on the same link (a 500 KB attachment at 20 KB/s held small documents for 25 seconds), and a peer stays in the presence graph during such a transfer, so presence does not mean up to date. Peer metadata reaches every device at about twice its size whenever a device joins or changes it. A document that many devices have written stays heavier on first sync and on every edit, and each map key removed with `UNSET` leaves about 54 bytes that reaping does not remove, so lists whose entries come and go belong in one document per entry. Observing Changes now says when an observer fires (`SELECT *` on every write to its documents, a projection only when a projected value changes, an aggregate on every write to the collection), that writing the same value from inside an observer loops, and that large observer results grow memory on every callback. The `ditto` plugin Skills (1.12.0) and the checklist (2.18) follow.
- Update the guide to version 3.9 with findings about directories, coordination, and long writes from SDK 5.1.0 and 5.2.0. A directory written with one Database ID opens with another and syncs its documents to the new database, and a directory that another process holds fails to open with `store/persistence-directory-locked`. A new section, Conditions and arithmetic across devices, shows that a conditional update is not a lock, that a bulk update covers only the documents a device has, and that `n = n + 1` loses increments even between online devices. Read-then-write sequences need a transaction even on one device, a read-write transaction or a large statement holds up incoming changes until it ends, receiving a large transaction holds up the receiver's own writes, and a large initial sync holds up the receiving device's other sync. The `ditto` plugin Skills (1.13.0) and the checklist (2.19) follow.
- Update the guide to version 3.10 with findings about observers, write rates, IDs, and collections from SDK 5.1.0 and 5.2.0. Observers are called at most about 30 times a second since 5.1, async JavaScript callbacks can leave an older result on screen, and garbage-collected JavaScript subscriptions and observers keep running. Frequent events are written several documents per `INSERT` (one document per statement topped out at about 600 a second), long ID lists use `USE IDS LIST` or chunks of 1,000, collections stay few because they cannot be dropped and slow down the first write to new ones as they accumulate, and alternatives are passed with `IN :values` instead of long or deeply parenthesized `OR` chains. The comparison of `DELETE`, soft delete, and `EVICT` now lists what each sends to other devices. The `ditto` plugin Skills (1.14.0) and the checklist (2.20) follow.
- Update the guide to version 3.11 with findings about storage, indexes, licenses, and relays from SDK 5.1.0 and 5.2.0. Deleted and evicted data frees space inside the files that later writes reuse, but SDK 5.2 shrinks the files only once the free space exceeds 100 MB by default (5.1.0 never does), small stores carry two WALs of about 20 MB, the WAL query takes the latest row of each key, and each write adds about 1.5 KB of on-disk log. Flagged documents slow queries until cleanup unless the flag is indexed, while tombstones do not; an index on a field with few values can be slower than no index. The offline license token's expiry is checked against the device clock when the token is set. Relays relay only what they subscribe to, also as carriers between sites that never connect, and the number of hops itself cost little in testing. The `ditto` plugin Skills (1.15.0) and the checklist (2.21) follow.
- Update the guide to version 3.12 with merge and query details from SDK 5.1.0 and 5.2.0. New notes say that the later write wins by when it was written, that a transaction's values still merge field by field with other devices' edits (`120 JPY`), that a long text field keeps one edit while a map of paragraphs keeps both, that the recommended shapes held with three devices, and that a randomized test of 396 rounds always converged. The `ditto` plugin Skills (1.16.0) and the checklist (2.22) follow.
- Update the guide to version 3.13 with DQL details from SDK 5.1.0 and 5.2.0. A single value or an empty array passed to `IN :values` matches nothing without an error, argument names take no colon, and `UPDATE`, `DELETE`, and `EVICT` without `WHERE` change every document without a warning, while `SET a.b` silently replaces a value of `a` that is not an object. Descending order lists documents without the sort field first, strings compare by code point, `LIKE` and identifiers are case-sensitive, division by zero is MISSING, and only a few keywords such as `collection` are rejected as names.
