# Platform Differences

The concepts, the DQL, and the sync behavior are the same in every SDK, but the APIs and some of their behavior differ. This page puts the four SDKs side by side, so that you can port code or read samples for another SDK. Each SDK page explains its column in detail, with code and the observations behind it: [Ditto on Flutter](../best-practices/platforms/flutter.md), [Ditto on JavaScript](../best-practices/platforms/javascript.md), [Ditto on Kotlin](../best-practices/platforms/kotlin.md), and [Ditto on Swift](../best-practices/platforms/swift.md). The behavior that we observed on SDK 5.1.0 and 5.2.0 is listed in the section "Behavior Specific to the ... SDK" of each SDK page.

## API Differences

| Topic | Flutter | JavaScript | Kotlin | Swift |
|---|---|---|---|---|
| Package | `ditto_live` (pub.dev) | `@dittolive/ditto` (npm) | `com.ditto:ditto-kotlin` (Maven Central) | `DittoSwift` (Swift Package Manager) |
| Create / open | `await Ditto.open(DittoConfig(...))`, or `Ditto.openSync` after `await Ditto.init()` | `await Ditto.open(config)`; on the Web, call `await init()` first | `DittoFactory.create(config)`, which does not suspend; its optional `CoroutineScope` (by default `MainScope()`) runs the callbacks | `try await Ditto.open(config:)`, or `Ditto.openSync(config:)` |
| System parameters at open (SDK 5.2+) | `DittoConfig(systemParameters: {...})` | `systemParameters` in the `DittoConfig` options | `DittoConfig(..., systemParameters = mapOf(...))` | `DittoConfig(..., systemParameters: [...])` |
| Start sync | `ditto.sync.start()` (`void`, throws on failure) | `ditto.sync.start()` | `ditto.sync.start()` (throws on failure) | `try ditto.sync.start()` |
| Shut down | `await ditto.close()` | `await ditto.close()` | `ditto.close()`, which waits for an open transaction | No `close()` in DittoSwift 5.1.0 and 5.2.0, although the 5.2.0 release notes announce one: release the last strong reference to the `Ditto` instance |
| Delete the local store (SDK 5.2+) | No API: after `close()`, delete the persistence directory | No API: after `close()`, delete the persistence directory | `DittoFactory.deleteStore(databaseId, persistenceDirectory)` | `Ditto.deleteStore(databaseID:persistenceDirectory:)` |
| Encryption at rest (SDK 5.2+) | Not available | Not available | `DittoConfig.encryptionKey` | `DittoConfig.encryptionKey` |
| Login failure | Returns an `AuthResponse` whose `exception` is set; does not throw | Returns a result whose `error` is set; does not throw | **Throws** `DittoException.AuthenticationException` | Reported to the completion handler as an error |
| Arguments | `arguments: {...}` (a `Map`) | A plain object as the second argument | A `Map`, or a serializable value | A dictionary (`arguments:`), or a `Codable` value |
| Query results | `items` is an `Iterable`; released by garbage collection | `items` is an array; released by garbage collection | Read inside the mapping function of `execute`; `executeRaw` returns a result that you `close()` | Released by automatic reference counting |
| Default observer | `registerObserver`, consumed through its `changes` stream | `registerObserver(query, handler, args)` | `registerObserver(query, args) { result -> }` (a suspending handler), or `observe(...)`, which returns a `Flow` | `registerObserver(query:arguments:deliverOn:handler:)`, delivered on the main queue by default |
| Observer backpressure | `registerObserver`: none. `registerObserverV2` (automatic, when its `changes` are consumed with `await for`) and `registerObserverWithSignalNext` (manual), both (Experimental) (SDK 5.1+) | `registerObserver` waits until a synchronous handler returns; an `async` handler is not awaited. `registerObserverWithSignalNext` for asynchronous work | The suspending handler and `collect` wait for your code; no `signalNext`. A slow `Flow` collector should `.conflate()` | `handler:` waits until it returns; `handlerWithSignalNext:` waits for `signalNext()` |
| Release observers and subscriptions | `cancel()` | `cancel()` | `close()` | `cancel()` |
| Differ | `Differ` | `Differ` | `DittoDiffer`, or a `DittoDiff` passed to the observer handler | `DittoDiffer` |
| Transaction completion | Return a value to commit; throw or return `TransactionCompletionAction.rollback` to roll back | Return a value to commit, or `'rollback'` | Must return `DittoTransaction.Result.Commit(value)` or `DittoTransaction.Result.Rollback` | Must return a value or `.commit` to commit, or `.rollback` |
| Attachments | `newAttachment` and `fetchAttachment`, which returns an `AttachmentFetcher` | `newAttachment` and `fetchAttachment`, which returns a fetcher | `newAttachment`, and a suspending `fetchAttachment` that reports progress to a callback | `newAttachment` and `fetchAttachment`, which returns a `DittoAttachmentFetcher` |
| Forward log events | `DittoLogger.customLogCallback` | `Logger.setCustomLogCallback` | `DittoLogger.observeLogEvents()`, a `Flow` | `DittoLogger.setCustomLogCallback(_:)` |

## Behavior Differences

What we observed on SDK 5.1.0 and 5.2.0. Each row names the section of the guide that gives the rule, and the section "Behavior Specific to the ... SDK" of each SDK page links to the observation behind its column.

| Behavior | Flutter | JavaScript | Kotlin | Swift |
|---|---|---|---|---|
| A dropped reference to an observer or a subscription ([Observer Lifecycle](../best-practices/observers.md#observer-lifecycle)) | Keeps running; release it explicitly | Keeps running; release it explicitly | Keeps running; release it explicitly | Keeps running; release it explicitly |
| An exception in an observer callback ([Observer Lifecycle](../best-practices/observers.md#observer-lifecycle)) | Reaches the zone; the observer keeps running, but a throwing `onChange` keeps its result out of `changes`, and a throw before `signalNext()` stops the observer | A synchronous throw is discarded; a rejected `async` callback is an unhandled rejection, which ends a Node.js process | Closes the observer, and is only logged | The handler cannot throw |
| Observer callbacks run on ([Keep observer callbacks fast](../best-practices/observers.md#keep-observer-callbacks-fast)) | The isolate that registered the observer | The event loop | The main thread, unless `DittoFactory.create` gets another scope | The main queue, unless `deliverOn:` names another |
| `ditto.store.execute` inside a transaction ([Transaction Rules](../best-practices/transactions.md#transaction-rules)) | Throws a `DittoException` | Writes never complete; reads complete but do not see the transaction's writes | Writes never complete; reads complete but do not see the transaction's writes | Writes never complete; reads complete |
| A read-write transaction started inside another ([Transaction Rules](../best-practices/transactions.md#transaction-rules)) | Waits until the outer one ends, so an outer callback that awaits it never ends | The same | The same | The same |
| Many writes that wait behind an open transaction ([Transaction Rules](../best-practices/transactions.md#transaction-rules)) | Wait until it ends (not tested with many) | Wait until it ends; 200 did | Each holds a thread; with 64 on `Dispatchers.IO`, the transaction could not resume | With as many as the CPU has cores (14 on our Mac), every task of the process stopped |
| Shutting down while a transaction is open ([Resource Cleanup and Shutdown](../best-practices/setup-and-lifecycle.md#resource-cleanup-and-shutdown)) | `close()` stops the isolate (in an app, the UI) | `close()` waits for the transaction | `close()` waits for the transaction | The release blocks its thread until the transaction ends (15 seconds for a transaction with 15 seconds left); the transaction commits |
| Writes in flight when Ditto shuts down ([Resource Cleanup and Shutdown](../best-practices/setup-and-lifecycle.md#resource-cleanup-and-shutdown)) | Their `Future`s fail; the writes were stored if the worker isolate of `execute` was already running, and none were if the first `execute` came right before `close()` | `close()` completes them | Stored, also when the call throws | 5.2.0: most fail with `useAfterCloseError` |
| Calls after shutdown ([Resource Cleanup and Shutdown](../best-practices/setup-and-lifecycle.md#resource-cleanup-and-shutdown)) | `execute` and `transaction` fail their `Future` with `DittoClosedException`; registrations and `sync` calls throw it at once | Throw or reject with a plain `Error` | Throw, except `sync.start()` | `transaction` throws; `execute` throws on 5.2.0 and ends the process on 5.1.0; registering an observer or a subscription, `sync.start()`, and `presence.graph` end the process |
| Opening a directory that this process has open ([One instance per persistence directory](../best-practices/setup-and-lifecycle.md#one-instance-per-persistence-directory)) | 5.2.0: fails after about 1 second. 5.1.0: never completes | Fails after about 1 second with `store/persistence-directory-locked` | Fails after about 1 second with `File already locked` | Fails after about 1 second with `persistenceDirectoryLocked` |
| Invalid DQL ([When a Statement Fails or Returns Nothing](../best-practices/dql.md#when-a-statement-fails-or-returns-nothing)) | `execute` fails; registering an observer or a subscription throws | `execute` rejects; registering an observer or a subscription throws | The call that receives it throws | The call that receives it throws |
| The arguments of a listed subscription registered without arguments ([Sync stop, close, and inspection](../best-practices/sync-and-subscriptions.md#sync-stop-close-and-inspection)) | Reading them ends the app | `queryArguments` is `null` | `queryArguments` is `null` | `queryArguments` is `nil` |
| Values that are not plain JSON ([Always pass values as parameters](../best-practices/dql.md#always-pass-values-as-parameters)) | `DateTime` becomes a string, `Uint8List` comes back as a list, a `BigInt` of 2^63 or more comes back as a `double` or as bytes, NaN and infinity fail, maps with `int` keys and classes without `toCbor()` fail | `Date` becomes `{}`, `undefined` becomes `null`, NaN and infinity fail, integers above 2^53 − 1 come back as `BigInt`, `Set` and functions become `{}`, `10.0` is stored as an integer | `Date`, `Instant`, `UUID`, and big numbers fail; NaN and infinity fail; a decimal that a 32-bit float holds exactly, such as `7.5`, comes back as a `FloatValue` | `Date` becomes an object, NaN and infinity fail, `UUID` becomes an uppercase string; a value that fits in 32 bits, such as `12.5`, comes back as a `Float`, which `as? Double` does not read |

Kotlin, Java, Swift, and C# stored some values incorrectly before SDK 5.2, and the upgrade does not correct data that was already written; see [Known Issues in SDK 5.1.0](upgrading.md#known-issues-in-sdk-510).
