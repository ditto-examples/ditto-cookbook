# Platform Differences

The concepts are the same on every platform, but some APIs behave differently. Keep these differences in mind when you port code or read samples for another SDK:

| Topic | Flutter | JavaScript | Swift | Kotlin |
|---|---|---|---|---|
| Create / open | `await Ditto.open(DittoConfig(...))` | `await Ditto.open(new DittoConfig(id, { mode: 'server', url }))`, or `new DittoConfig({ databaseID, connect, ... })` (SDK 5.2+); on the Web, call `await init()` first | `try await Ditto.open(config:)` | `DittoFactory.create(config)` |
| System parameters at open (SDK 5.2+) | `DittoConfig(systemParameters: {...})` | `systemParameters` in the `DittoConfig` options | `DittoConfig(..., systemParameters: [...])` | `DittoConfig(..., systemParameters = mapOf(...))` |
| Start sync | `ditto.sync.start()` (`void`, throws on failure) | `ditto.sync.start()` | `try ditto.sync.start()` | `ditto.sync.start()` (throws on failure) |
| Close | `await ditto.close()` | `await ditto.close()` | `Ditto.close()` (SDK 5.2+). In 5.1 there is no public `close()`: release all references, and the instance shuts down when deallocated | `ditto.close()` |
| Delete the local store (SDK 5.2+) | No API; after `close()`, delete the persistence directory (evicted values stay in the files; see [Most deleted and evicted values remain in the database files](observations/storage-and-deletion.md#most-deleted-and-evicted-values-remain-in-the-database-files)) | No API; after `close()`, delete the persistence directory (see [Deleting the directory after close() leaves no data behind](observations/persistence-directory.md#deleting-the-directory-after-close-leaves-no-data-behind)) | `Ditto.deleteStore(databaseID:persistenceDirectory:)` | `DittoFactory.deleteStore(databaseId, persistenceDirectory)` |
| Encryption at rest (SDK 5.2+) | Not available | Not available | `DittoConfig.encryptionKey` | `DittoConfig.encryptionKey` |
| Login failure | Returns `AuthResponse` with `exception`; does not throw | Returns a result with `error`; does not throw | Reported to the completion handler as `error` | **Throws** |
| Observer backpressure | `registerObserver`: none. `registerObserverV2` (automatic) and `registerObserverWithSignalNext` (manual), both (Experimental) (SDK 5.1+) | `registerObserver` signals the next update when a synchronous handler returns (async handlers are not awaited; see [In JavaScript, registerObserver does not await async callbacks](observations/observer-behavior.md#in-javascript-registerobserver-does-not-await-async-callbacks)); use `registerObserverWithSignalNext` for async work | `registerObserver(... handler:)` signals automatically; `handlerWithSignalNext:` is manual | No `signalNext`: suspend handlers and `collect` wait for the handler; `observe` returns a `Flow` |
| Release observers and subscriptions | `cancel()` | `cancel()` | `cancel()` | `close()` |
| Transaction completion | Return a value to commit; throw or return `TransactionCompletionAction.rollback` to roll back | Return a value to commit, or `'rollback'` | Return a value to commit, or `.rollback` | Must return `DittoTransaction.Result.Commit(value)` or `DittoTransaction.Result.Rollback` |
| `ditto.store.execute` inside a transaction | Throws `DittoException` | Writes deadlock without an exception, and reads do not see the transaction's writes; never do it (see [In JavaScript, store.execute writes inside a transaction deadlock](observations/transaction-behavior.md#in-javascript-storeexecute-writes-inside-a-transaction-deadlock)) | Can deadlock; never do it | Can deadlock; never do it |
| Read-write transaction nested inside a read-write transaction | Deadlocks (the SDK does not detect it); never do it | Deadlocks; never do it | Can deadlock; never do it | Can deadlock; never do it |

See [Observing Changes](../best-practices/observers.md) and [Transactions](../best-practices/transactions.md) for details on each platform's patterns. In the JavaScript SDK, values that are not plain JSON need care (in our testing with SDK 5.1.0 and 5.2.0): a `Date` is stored as `{}`, `undefined` as `null`, `NaN` and `Infinity` make the write fail, a `Uint8Array` round-trips as bytes, and integers above 2^53 − 1 come back as `BigInt`, which `JSON.stringify` cannot serialize (see [JavaScript values that are not plain JSON change when stored](observations/dql-behavior.md#javascript-values-that-are-not-plain-json-change-when-stored)).

Other behavior of the JavaScript SDK that we observed with SDK 5.0.3, 5.1.0, and 5.2.0 (each item links to its observation):

- An exception thrown in an observer callback is discarded: the observer keeps being called, and neither `uncaughtException` nor `unhandledRejection` reports it. Catch and log errors inside the callback (see [In JavaScript, exceptions in observer callbacks are discarded](observations/observer-behavior.md#in-javascript-exceptions-in-observer-callbacks-are-discarded)).
- `item.value` returns the same object every time, and changes to it are kept in that object but never reach the store. Copy the value before you modify it for display. The `value` and `jsonString()` of a result could still be read after `ditto.close()`, also for items that had not been read before (see [In JavaScript, query results return the same objects](observations/observer-behavior.md#in-javascript-query-results-return-the-same-objects)).
- `ditto.store.observers` exists since 5.0 and also counts observers from `registerObserverWithSignalNext`, but its elements are not the objects that the registration returned; compare counts, not objects (see [In JavaScript, store.observers exists since 5.0 and lists other objects](observations/observer-behavior.md#in-javascript-storeobservers-exists-since-50-and-lists-other-objects)).
- A Node.js script that does not start sync (a seed, migration, or command-line script) must keep the event loop alive while it awaits `ditto.store.transaction()`, for example with a timer that it clears afterwards. Without that, the process ended with a panic (`Panic: Error { status: PendingException ... }`, exit code 134 or 139) before the transaction finished, in every run on 5.0.3 to 5.2.0. With sync started, the same transaction completed, and `store.execute` alone was not affected (see [A Node.js script that keeps neither sync nor a timer running ends with a panic while awaiting a transaction](observations/transaction-behavior.md#a-nodejs-script-that-keeps-neither-sync-nor-a-timer-running-ends-with-a-panic-while-awaiting-a-transaction)).
- `ditto.close()` waits for open transactions and other running operations (see [Concurrency and Duration](../best-practices/transactions.md#concurrency-and-duration) and [In JavaScript, close() waits for open transactions](observations/transaction-behavior.md#in-javascript-close-waits-for-open-transactions)), including `execute()` calls started right after `close()` was called; 200 writes that were not awaited were all stored. Calls made after `close()` has completed fail with `Can't perform operation using a Ditto instance that has been closed.` (see [In JavaScript, close() completes pending writes](observations/transaction-behavior.md#in-javascript-close-completes-pending-writes)).
- Opening a persistence directory that is already open fails within 10 seconds with `File already locked, ...` (see [In JavaScript, opening an open directory again fails](observations/persistence-directory.md#in-javascript-opening-an-open-directory-again-fails)).
- Logs are exported with `Logger.exportToFile(path)`. Each line has `timestamp`, `level`, `message`, `target`, `span`, `spans`, and `threadId`. An existing file fails with `File exists (os error 17)`, and a missing directory with `No such file or directory (os error 2)` (see [Exported logs include debug lines regardless of the console level](observations/configuration-and-diagnostics.md#exported-logs-include-debug-lines-regardless-of-the-console-level)).

Kotlin, Java, Swift, and C# stored some values incorrectly before SDK 5.2, and the upgrade does not correct data that was already written; see [Known Issues in SDK 5.1.0](upgrading.md#known-issues-in-sdk-510).
