# Upgrading from SDK 5.1

To upgrade, change the dependency to 5.2.0; most apps need no code changes. SDK 5.2 syncs with devices on earlier 5.x releases, so you can roll it out gradually. While you do, some devices still run 5.1.0: the [known issues of that release](#known-issues-in-sdk-510) apply to them, and [Mixed Releases](#mixed-releases) describes what differs while releases are mixed.

## Changes in SDK 5.2.0

Review these changes when you upgrade:

- **System parameters** can be passed in `DittoConfig.systemParameters`, which applies them before Ditto starts and makes `Ditto.open()` fail on an unknown name or a wrong type. Move the settings your app applies with `ALTER SYSTEM` after every open into the configuration (see [Applying System Parameters](../best-practices/setup-and-lifecycle.md#applying-system-parameters)).
- **`DQL_REQUEST_HISTORY_SIZE`** defaults to 128 entries instead of 4096. Set it explicitly if your diagnostics read more of `system:request_history`.
- **`_id` in observer rows**: in our testing, the rows that 5.2.0 observers deliver for a query that does not project `_id` have no `_id`, and the rows of a join no composite `_id`, while 5.1.0 included them; Flutter's `registerObserver` still includes them. Project `_id`, or the keys of a joined row, wherever you diff or key the rows (see [On SDK 5.2.0, observer rows include _id only when it is projected, except with Flutter's registerObserver](observations/observer-behavior.md#on-sdk-520-observer-rows-include-_id-only-when-it-is-projected-except-with-flutters-registerobserver)).
- **Request history threshold**: in our testing with the JavaScript, Kotlin, and Swift SDKs, 5.2.0 with the default qualifiers recorded only queries that took about 10 seconds or more in `system:request_history`, while 5.1.0 recorded queries of 3 seconds. Set `DQL_REQUEST_HISTORY_QUALIFIERS` to `{'threshold': 1000}` if your diagnostics read slow queries from it (see [On SDK 5.2.0, the request history records queries of about 10 seconds or more by default](observations/configuration-and-diagnostics.md#on-sdk-520-the-request-history-records-queries-of-about-10-seconds-or-more-by-default)).
- **Flutter persistence directory**: the default root directory moves to the application support directory. With `persistenceDirectory: null`, existing data is still found; with a relative path, check that upgraded installations still open their data (see [DittoConfig](../best-practices/setup-and-lifecycle.md#dittoconfig)).
- **Oversized documents**: according to the release notes, a device drops a replication diff that would push a document over the hard size limit, and lists the document in `system:sync_degradations`; our testing showed the same (see [Document Size Limits](../best-practices/data-modeling.md#document-size-limits) and [On SDK 5.2.0, an oversized merge leaves devices with different versions](observations/documents-and-limits.md#on-sdk-520-an-oversized-merge-leaves-devices-with-different-versions)).
- **Observers on virtual collections** fire when the data changes instead of on a timer, for most collections. Code that relied on periodic callbacks should query on its own schedule. Observers on `system:system_info` still fire often (see [Monitoring Storage](../best-practices/deletion-and-storage.md#monitoring-storage) and [Observers of system:system_info keep firing while nothing changes](observations/observer-behavior.md#observers-of-systemsystem_info-keep-firing-while-nothing-changes)).
- **SQLite write-ahead log**: the size monitor and the automatic reclaim of free space are on by default (see [Monitoring Storage](../best-practices/deletion-and-storage.md#monitoring-storage)).
- **Android permissions**: `DittoSyncPermissions.requiredPermissions()` no longer includes the permissions for multicast (see [Multicast (Beta) (SDK 5.1+)](../best-practices/setup-and-lifecycle.md#multicast-beta-sdk-51)).
- **Kotlin**: `newAttachment` overloads that take `Map<String, Any?>` metadata are deprecated and throw `IllegalArgumentException` for values that are not strings; use the `Map<String, String>` overloads. The encryption example of the Kotlin 5.2.0 release notes calls `Ditto.open(config)`, which the Kotlin SDK does not have; use `DittoFactory.create(config)` (see [Behavior Specific to the Kotlin SDK](../best-practices/platforms/kotlin.md#behavior-specific-to-the-kotlin-sdk)).
- **Swift `close()`**: the 5.2.0 release notes announce a `close()` method, but in our testing the DittoSwift 5.2.0 package had none, as 5.1.0 did not; Swift apps still shut Ditto down by releasing the last strong reference (see [Closing Ditto in Swift](../best-practices/platforms/swift.md#closing-ditto-in-swift) and [In Swift 5.2.0, Ditto has no close() method](observations/swift-sdk.md#in-swift-520-ditto-has-no-close-method)).
- **Flutter: closing and reopening Ditto in one process**: in our testing on 5.2.0, but not on 5.1.0, a `SyncSubscription` or `Transaction` object of a closed instance that was garbage-collected stopped the next `Ditto.open()` or `close()` in the same process, without an error. Avoid closing and reopening Ditto in one process, keep subscription objects reachable when you must, and close test stores after the last test of a file (see [Subscriptions in Flutter](../best-practices/platforms/flutter.md#subscriptions-in-flutter) and [In Flutter 5.2.0, dropped subscription and transaction objects of a closed instance stop the next open or close](observations/flutter-sdk.md#in-flutter-520-dropped-subscription-and-transaction-objects-of-a-closed-instance-stop-the-next-open-or-close)).
- **Data Streams**: if you set `NGN_SYNC_ENABLED`, also set `NGN_DATA_STREAMS_ENABLED`; otherwise `ditto.sync.start()` now fails with a configuration error.
- **New features** that this guide describes: [support bundles](../best-practices/logging-and-observability.md#support-bundles-sdk-52), `system:sync_degradations` and new metrics ([System Virtual Collections](system-reference.md#system-virtual-collections)), WAL values in [Monitoring Storage](../best-practices/deletion-and-storage.md#monitoring-storage), `ditto.store.observers` ([Resource Cleanup and Shutdown](../best-practices/setup-and-lifecycle.md#resource-cleanup-and-shutdown)), `logout(cleanup:)` ([Authentication](../best-practices/setup-and-lifecycle.md#authentication)), and encryption at rest for Swift and Kotlin ([Data at Rest](../best-practices/security.md#data-at-rest)).

See the [release notes](https://docs.ditto.live/release-notes) for the complete list; their platform filter shows the changes of each SDK.

## Known Issues in SDK 5.1.0

SDK 5.2.0 fixes the following issues of 5.1.0. They apply to every device that still runs 5.1.0. Items that say "in our testing" were reproduced with the JavaScript SDK 5.1.0 on Node.js and, except for the attachment fetch below and an index that the 5.1.0 migration had already broken, did not occur with 5.2.0; the others come from the 5.2.0 release notes.

**Wrong results without an error**

- **`DELETE` or `EVICT` with `USE IDS` and no `WHERE` predicate removes nothing.** This applies to `USE IDS 'a'`, `USE IDS LIST :ids`, and `USE IDS ... WHERE true`; the statement completes without an error and `mutatedDocumentIDs()` is empty (in our testing; see [On SDK 5.1.0, DELETE and EVICT with USE IDS and no WHERE predicate remove nothing](observations/dql-behavior.md#on-sdk-510-delete-and-evict-with-use-ids-and-no-where-predicate-remove-nothing)). Use `WHERE _id IN :ids`, which is planned as an ID scan and works on every release.
- **A composite index that mixes `ASC` and `DESC` keys returns results in the wrong order.** In our testing, with an index on `(status, createdAt DESC)`, `SELECT * FROM orders WHERE status = :status ORDER BY createdAt DESC` returned the oldest documents first, and with `LIMIT 2` it returned the two oldest; the plan had no sort step. A range condition on the second key (`createdAt >= :since`) behaved the same way. `ADVISE` suggests such indexes on 5.1.0 as well. On 5.1.0, define composite indexes with keys in one direction, such as `(status, createdAt)`: the planner then adds a sort step, and the order is correct (see [On SDK 5.1.0, composite indexes with a descending key return rows in the wrong order](observations/dql-behavior.md#on-sdk-510-composite-indexes-with-a-descending-key-return-rows-in-the-wrong-order)).
- **`ORDER BY` on projected fields can be ignored in index plans.** In our testing, with an index on `(status, createdAt)`, `SELECT _id, createdAt FROM orders WHERE status = :status ORDER BY createdAt DESC` returned the rows in insertion order, while `SELECT *` sorted them correctly (see [On SDK 5.1.0, ORDER BY on a projected field was ignored in an index plan](observations/dql-behavior.md#on-sdk-510-order-by-on-a-projected-field-was-ignored-in-an-index-plan)). Use `SELECT *` for sorted queries that use an index, or sort in your code.
- **`ANY ... SATISFIES` with a condition on several properties matches every document.** In our testing, `WHERE ANY car IN cars SATISFIES car.color = 'blue' AND car.type = 'SUV' END` matched all three test documents instead of one, so the same condition in an `UPDATE` or `DELETE` changes every document. The same expression in a projection returned the correct value, and 5.0.3 returned the one document, so the issue came with 5.1.0 (see [On SDK 5.1.0, ANY with a condition on several properties matched every document](observations/dql-behavior.md#on-sdk-510-any-with-a-condition-on-several-properties-matched-every-document)). Do not use such conditions in `WHERE` on 5.1.0; select the candidates and test the condition in a projection or in your code.
- **A comparison with the constant on the left can return wrong results through an index.** In our testing, with an index on `a`, `WHERE 1 < a` returned no documents and `WHERE 2 >= a` returned one, instead of two and three; 5.0.3 had the same issue (see [Before SDK 5.2.0, a comparison with the constant on the left returned wrong rows through an index](observations/dql-behavior.md#before-sdk-520-a-comparison-with-the-constant-on-the-left-returned-wrong-rows-through-an-index)). Write the field on the left (`a > 1`).
- **Values stored incorrectly by some SDKs.** Kotlin and Java stored and compared negative integers passed in map arguments as one less (`-5` as `-6`). Swift stored booleans created with `JSONSerialization` as `0` and `1`. C# decoded unsigned integers above `Int64.MaxValue` as `null`. Upgrading does not correct data that was already written: find and fix the affected values.

**Failures and hangs**

- `INSERT` into an indexed collection that was empty before an upgrade from 5.0.x fails with `no such table: ___idx_coll_...`. In our testing, a store migrated by 5.1.0 kept failing after a later upgrade to 5.2.0, while a store upgraded from 5.0.3 directly to 5.2.0 worked; drop and re-create the index to repair it (see [An index created on an empty collection breaks in the 5.1.0 migration](observations/dql-behavior.md#an-index-created-on-an-empty-collection-breaks-in-the-510-migration) and [Upgrading and downgrading](../best-practices/indexing-and-performance.md#upgrading-and-downgrading)).
- `SELECT` statements with long `AND` or `OR` chains in `WHERE` can crash the app. In our testing with the JavaScript SDK 5.1.0, 15,000 `OR` terms (or 20,000 `AND` terms) ended the process without an exception, while 10,000 worked; 5.2.0 handled 50,000 `OR` terms (see [Long OR chains crashed SDK 5.1.0](observations/dql-behavior.md#long-or-chains-crashed-sdk-510)). Devices with smaller thread stacks may fail with fewer terms. Use `IN :values` for long lists of alternatives.
- Observers can stall when many are active at the same time. In our testing with the JavaScript SDK on one Mac, with 60 or more store observers on 5.1.0 (35 or more on 5.0.3), a change no longer reached any callback, without an exception: with the observers registered at once, only the log showed an error (`BeginTransactionTimeout`), and with the observers registered one by one, nothing was logged; cancelling most of them did not recover the others. On 5.2.0, 1,000 observers worked (see [On SDK 5.1.0, observers stall beyond about 60](observations/observer-behavior.md#on-sdk-510-observers-stall-beyond-about-60)). The threshold may differ on other devices. While devices still run 5.1.0, do not register one observer per row of a list.
- In rare cases, completing a write transaction could hang or cancel another write transaction in progress.
- A fetch of an attachment that no document references anymore retries forever instead of ending. The 5.2.0 release notes list this as fixed, but in our testing 5.2.0 ended only a fetch that a device started after it had deleted the document and opened its store again; a fetch that was already waiting, and one whose holder had collected the blob, stayed pending on 5.2.0 as well (see [A fetch of a collected blob stays pending instead of ending with Deleted](observations/attachment-behavior.md#a-fetch-of-a-collected-blob-stays-pending-instead-of-ending-with-deleted) and [A fetch waits while no device holds the blob, and a device that deleted the document still serves it](observations/attachment-behavior.md#a-fetch-waits-while-no-device-holds-the-blob-and-a-device-that-deleted-the-document-still-serves-it)); keep a stall timeout on both releases (see [Fetching Attachments](../best-practices/attachments.md#fetching-attachments)).
- Peers that authenticate right after a certificate revocation is created are rejected, although a revocation should apply only to certificates issued before it (see [Certificate Revocation (SDK 5.1+)](../best-practices/security.md#certificate-revocation-sdk-51)).
- Flutter: hot restarting an app while a store observer is active during sync can crash it, and `Ditto.open()` can crash on 32-bit Android devices that report the `armv8l` architecture.

## Mixed Releases

In our testing, peers on 5.1.0 and 5.2.0, and on 5.0.3 and 5.2.0, synced in both directions, merged concurrent edits to the same documents as on a single release, and fetched attachments from each other (see [Peers on different releases merged to the same documents](observations/merge-behavior.md#peers-on-different-releases-merged-to-the-same-documents)). Each peer saw the other's `dittoSdkVersion` in its presence graph, which helps to find the devices that still run an older release (see [Presence shows each peer's SDK version](observations/connections-and-presence.md#presence-shows-each-peers-sdk-version)).

Two results differ while releases are mixed:

- **A merge that pushes a document over the hard size limit** ends differently on each release: a device on 5.1.0 keeps the oversized document and cannot update it, a device on 5.2.0 keeps only its own part, and a device on 5.0.3 keeps the document and can still update it (see [An oversized merge ends differently on each release](observations/documents-and-limits.md#an-oversized-merge-ends-differently-on-each-release)). The protection is the same on every release: keep documents far below the limit (see [Document Size Limits](../best-practices/data-modeling.md#document-size-limits)).
- **Deeply nested documents**: on devices on 5.0.3, every query on a collection that held a document 30 or more levels deep ended the process, also when the document had arrived through sync from a device on a later release (see [Very deep documents end a peer's process during sync](observations/documents-and-limits.md#very-deep-documents-end-a-peers-process-during-sync)). Keep nesting shallow (see [Flat or nested](../best-practices/data-modeling.md#flat-or-nested)).

## Rolling Back

SDK 5.2 does not change the on-disk store format, so an app can go back from 5.2 to 5.1 without special steps. To go back to 5.0 or v4, go through SDK 5.0.2 or later (or 4.14.6 or later), which convert the 5.1 index format back (see [Upgrading and downgrading](../best-practices/indexing-and-performance.md#upgrading-and-downgrading)). In our testing, a store moved between 5.2.0 and 5.1.0 in both directions kept its documents and indexes, and on 5.0.3 a composite index became single-field indexes (see [An index created on an empty collection breaks in the 5.1.0 migration](observations/dql-behavior.md#an-index-created-on-an-empty-collection-breaks-in-the-510-migration)). As with any upgrade, test the procedure with representative application data before you deploy it.
