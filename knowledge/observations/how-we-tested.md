# How We Tested

The knowledge pages describe how Ditto behaved when we ran it, next to what Ditto's documentation says. This page describes how we ran it, so that you can judge how far a result carries over to your app. Each observation names the SDK releases and the number of runs it is based on; this page explains the setup they share.

## Test Environment

- **SDK**: observations of Ditto itself (merges, queries, sync, storage) ran with the JavaScript SDK (`@dittolive/ditto`) 5.0.3, 5.1.0, and 5.2.0 on Node.js 24, on one Mac. Most of them compare 5.1.0 and 5.2.0; 5.0.3 was added where a difference between releases mattered.
- **SDK behavior**: the behavior of each SDK's API (callbacks, transactions, errors, values, shutdown) was observed with the same set of checks on all four SDKs, each on 5.1.0 and 5.2.0, on the same Mac: Flutter (`ditto_live`, Flutter 3.47.8) on macOS, Kotlin (`com.ditto:ditto-kotlin`) on an Android 16 emulator (API 36, arm64), Swift (`DittoSwift`, Xcode 26.6) on macOS, and JavaScript on Node.js 24. Checks whose result could depend on the operating system also ran on an iOS 26.5 simulator (Swift and Flutter). Each SDK page links to the observations of its SDK: [Flutter SDK Behavior](flutter-sdk.md), [JavaScript SDK Behavior](javascript-sdk.md), [Kotlin SDK Behavior](kotlin-sdk.md), and [Swift SDK Behavior](swift-sdk.md).
- **Peers**: Small Peers in small-peers-only mode with an offline license token, each in a new persistence directory. The peer-to-peer transports (Bluetooth LE, LAN discovery, AWDL) were disabled, and the peers connected over TCP on `127.0.0.1`: one peer (the hub) listened on a port, and the others listed it in `connect.tcpServers`. A peer that only connects still listens on all interfaces (see [A device that only connects over TCP also listens for TCP connections](connections-and-presence.md#a-device-that-only-connects-over-tcp-also-listens-for-tcp-connections)); since we found that, every peer also listens on `127.0.0.1` only. The results that we ran again with this setting did not change, except one: on 5.1.0, whether a hub at its connection limit stopped replacing connections varied with this setting and from run to run (see [At-capacity actions 1 and 2 admit extra clients but keep replacing connections](connections-and-presence.md#at-capacity-actions-1-and-2-admit-extra-clients-but-keep-replacing-connections)).
- **Processes**: most observations ran several Ditto instances in one process (Node.js, or the test app of the other SDKs). Observations that needed different SDK releases, a peer that crashes or is suspended, or a different clock per peer ran each peer in its own process.
- **Relay**: to see what travels between two peers, a TCP relay sat between them. It counted the bytes in each direction, could limit each direction to a bandwidth (a slow link such as Bluetooth LE), and could pause the traffic without closing the connections (a network that stops passing data, as when Wi-Fi drops), then deliver what it had held. The relay itself buffers about 20 ms of traffic, at least 64 KiB.
- **Clocks**: to give one peer a clock that runs ahead or behind, its process ran with a library that shifts the wall clock by a set offset. Ditto's `clock()`, its log timestamps, and `Date.now()` all followed the shifted clock, while timers and timeouts kept working, because the monotonic clock was not shifted. Peers in one process share one clock, so only peers in separate processes can have different clocks.

## Reading the Results

- **Runs**: "three runs each" means that the same procedure was repeated three times on each listed release. Timing results were repeated at least three times before we drew a conclusion; results from a single run say so. "Deterministic" means that every run gave the same result.
- **Numbers**: times, sizes, and rates come from one machine over loopback TCP. Phones, real networks, and other transports will differ, often by a lot. Times also changed on the same machine: in the last full run, which came after an update of its operating system, changes that the entries show reaching other devices within tens of milliseconds often took twice as long or more (see Full runs below). Use the numbers for the order of magnitude and for the shape of the behavior (what waits for what, what grows with what), not as estimates for your app, and compare the numbers within an entry rather than across entries.
- **Releases**: when a result differs between releases, the observation gives each release's value. The best-practices pages carry the same information as labels such as **Note (SDK 5.1.0 and 5.2.0)**.
- **Documentation**: when Ditto's documentation, API reference, or release notes describe the behavior, the observation says so and whether we saw the same.
- **Scope**: what an observation did not cover is listed under "Not tested". The limits of the environment above apply to every observation.

## What We Did Not Test

- Physical mobile devices: the Kotlin observations ran on an Android emulator, and the Swift and Flutter observations on macOS and an iOS simulator. Flutter on Android, Windows, Linux, and the Web, and the JavaScript SDK in browsers and React Native
- Observations of Ditto itself with SDKs other than JavaScript: merges, queries, and sync behave the same in every SDK according to Ditto's documentation, but we did not repeat those observations with the other SDKs
- Bluetooth LE, AWDL, Wi-Fi Aware, LAN discovery, and multicast; a slow or paused link was simulated with the relay
- Ditto Server, its HTTP API, and authentication through a webhook
- Real networks between machines, and more devices than each observation names

## Checks of the Guide Itself

These checks run on every change of the guide:

- **DQL statements**: every DQL statement in the guide, about 390 from the `sql` code blocks and from the Dart code passed to `execute`, observers, and subscriptions, runs in a new, empty store on 5.1.0 and 5.2.0 (and 5.0.3 when needed), with the arguments of its `-- Arguments:` comment (about 150 statements) or with placeholder arguments. An `-- Arguments:` comment must be valid JSON and name exactly the parameters of its statement. The only statements that fail are those that the guide presents as errors, joins that need an index (an empty store has none, as [Index requirement](../../best-practices/dql.md#index-requirement) describes), and, on 5.1.0, the statements that use features marked (SDK 5.2+).
- **Expression examples**: every `expression` → `result` example in the guide is evaluated with `SELECT <expression> AS v FROM system:dual` and compared with the stated result; on 5.1.0 and 5.2.0 all of them matched (the `clock()` examples are checked for their type only). On 5.0.3, `serialize_json()` does not exist. One example shows a detail worth knowing: `tz_offset('America/New_York', 'TZN')` returned `-300` on 2026-10-31, while daylight saving time was in effect. With `'TZN'`, the function returns the offset in force on 1970-01-01, not the current one. The rules that the functions page states in its text, rather than as examples, were checked separately (see [The function rules of DQL Functions and Operators held on SDK 5.1.0 and 5.2.0](dql-behavior.md#the-function-rules-of-dql-functions-and-operators-held-on-sdk-510-and-520)).
- **Full runs**: from 2026-11-03 to 2026-11-04, all of our checks ran in one pass, one check at a time, on 5.2.0 (289 checks) and on 5.1.0 (287 checks), without errors, timeouts, or crashes. Every check that tests a claim of the guide gave the same verdict as in its previous run, apart from one whose verdict rule we had corrected. The times differed: changes that the entries show reaching other devices within tens of milliseconds often took twice as long or more, also in checks that we ran on their own after the pass, while those that took about a second changed little, and other times came out longer or shorter, a few of them by much more. The difference began between our runs of 2026-11-01 and this pass, a period in which the operating system of the Mac was updated; we did not find what caused it. Each entry gives the times of its own runs.
- **SDK code**: the code on each SDK page and in the Skills' `examples/<sdk>/` was built against SDK 5.2.0, and the examples that can run without Ditto Server, a real device, a network listener, or the default storage location, and that do not stop the process on purpose, ran against local stores, with checks of the results that the page states. Flutter: 91 blocks and 26 files built on macOS, and the tests of the page and of the Skills (24 tests) ran; the widget, attachment, presence, and transport examples were only built. JavaScript: 92 blocks and 26 files on Node.js 24, with 74 checks and 13 tests for the page and 24 checks and 12 tests for the Skills; the React examples ran with jsdom. Kotlin: 98 blocks (all but the Gradle and import snippets) and 26 files on the Android emulator, with 64 checks for the page and 34 for the Skills. Swift: 91 blocks (all but `Package.swift`) and 26 files built on macOS and the iOS simulator, and 59 steps of the page ran on both. Examples of APIs added in 5.2 were not run on 5.1.0; what the SDK pages say about 5.1.0 comes from the observation entries.
