What this means

Pin the exact SDK version in your dependency file so that every developer and every CI build uses the same release: ditto_live in pubspec.yaml (Flutter), @dittolive/ditto in package.json (JavaScript), com.ditto:ditto-kotlin in your Gradle file (Kotlin), or DittoSwift through Swift Package Manager (Swift). Then check the requirements of SDK 5.2.0 on your SDK's page of the guide:

  • Request the Bluetooth, local network, and nearby-device permissions that peer-to-peer sync needs before sync starts
  • Flutter: Dart 3.5.4+ and Flutter 3.24.5+; iOS 15+ and macOS 12+ on arm64 only (Intel Macs and x86_64 simulators are not supported), with CocoaPods; Android minSdk 24, set explicitly in your app's Gradle file, and Kotlin Gradle plugin 2.0+
  • Flutter Web: data is kept in memory only, sync works only over WebSocket with Ditto Server, and indexes are not supported
Why this matters

Without a pinned version, developers, CI, and devices can end up on different SDK releases. Missing permissions and unsupported architectures are found late: they usually show up as peers that never connect, not as a clear error.

What this means

SDK 5.2 syncs with devices on earlier 5.x releases, so you can roll out the upgrade gradually. Until every device runs 5.2.0, avoid the 5.1.0 issues that return wrong results without an error:

  • Target DELETE and EVICT with WHERE _id IN :ids, not with USE IDS alone
  • Keep all keys of a composite index in one direction, such as (status, createdAt), also for indexes that ADVISE suggests
  • Use SELECT * for sorted queries that use an index, or sort in your code
  • Do not test several properties of an array element in one ANY ... SATISFIES condition in WHERE
  • Write the field on the left of a comparison (a > 1, not 1 < a)

In Flutter, before you release the upgrade, check on every platform you ship that an installation that passes a relative persistenceDirectory still opens its existing data. If your diagnostics read system:request_history, set DQL_REQUEST_HISTORY_SIZE explicitly: its default drops from 4096 to 128 entries. To find the devices that still run an older release, read dittoSdkVersion of the peers in the presence graph.

Why this matters

In our testing, peers on 5.1.0 and 5.2.0 merged concurrent edits to the same documents, but a merge that pushed a document over the hard size limit ended differently on each release. These 5.1.0 issues raise no error, so they look like missing, misordered, or unexpectedly changed data. For example, an index that mixes ASC and DESC keys returns rows in the wrong order (with LIMIT, the wrong rows), and a multi-property ANY ... SATISFIES condition matches every document, so an UPDATE or DELETE that uses it changes them all. SDK 5.2.0 fixes these issues but does not repair data written before the upgrade: Kotlin and Java apps on 5.1 stored negative integers passed in map arguments as one less (-5 as -6). In Flutter since 5.2, a relative persistenceDirectory is resolved against the application support directory, and only persistenceDirectory: null falls back to the previous default location. SDK 5.2 keeps the on-disk format of 5.1, so an app can go back to 5.1 without special steps.

What this means

Open Ditto once at app start and pass the instance to the parts of the app that need it, for example through dependency injection or a service object. If several callers may open Ditto at the same time, let them all wait for the same pending open. Never open a new instance per screen or request, and never reopen a directory before closing has completed. Never read, write, or delete files inside the persistence directory, and never copy it to another device. To remove the local data, use deleteStore in Kotlin and Swift (SDK 5.2+); in Flutter and JavaScript, delete the whole directory after closing has completed.

Why this matters

What happens when the same process opens a directory that it already has open differs by SDK: in Flutter (SDK 5.1.0), the second open may never complete, and it does not throw, so the code that awaits it stops without any error. Only one Ditto instance can use a persistence directory at a time; while another process holds it, opening Ditto fails with store/persistence-directory-locked. Include the Database ID in a path you choose: a directory written with another Database ID opens without an error, and its documents sync to the new database. The directory also holds the device's identity and its sync state, so a copied or partly deleted directory breaks sync without an error: in our testing with SDK 5.1.0 and 5.2.0, a copy and the original never converged, and a device that reopened its directory without ditto_store did not send some of its new documents. A copy that replaced the original, which was never opened again, synced normally; if both have run, delete the whole directory of one of them so that it syncs again with a new identity.

What this means

Choose the connection mode of DittoConfig for each build:

  • A server connection with the Server URL: devices sync through Ditto Server and with each other, and must authenticate. Copy the Server URL from the Ditto Portal exactly as shown.
  • Small-peers-only with a private key: devices sync only with each other, using a shared key (TLS 1.3).
  • Small-peers-only without a key: for local store tests and development only. Sync in this mode still requires an offline license token.
Why this matters

The mode decides how devices authenticate and whether traffic is encrypted. Without a private key, peers do not authenticate each other: any device that has the SDK, the Database ID, and an offline license token can connect, read, and write. The SDK documents this mode as unencrypted in transit, so treat it as unprotected. Also make sure that the Database ID is a valid UUID: do not count on opening Ditto to reject a leftover placeholder.

For small-peers-only deployments, obtain an offline license token from Ditto and set it with setOfflineOnlyLicenseToken before you start sync. Read the token and the shared key from secure provisioning, never from source code. No expiration handler is needed in this mode.

What this means

With a server connection, set the expiration handler on ditto.auth before starting sync. Inside the handler:

  • Fetch a fresh token from your backend and call login with the token and your provider name
  • Check the login result the way your SDK reports it: in Flutter, login returns an AuthResponse whose exception is set, and in JavaScript a result whose error is set, without throwing; in Kotlin, login throws; in Swift, the completion handler receives the error
  • Catch errors from your own token code and report them; never let an error escape from the handler
Why this matters

With a server connection, starting sync fails if no handler is set. Ditto calls the handler again before the credentials expire, so reusing a cached token makes the refresh fail. An error that escapes from the handler never reaches Ditto and becomes an unhandled error in your app.

What this means

Put the system parameters that your app always needs in the system parameters of DittoConfig (SDK 5.2+), in one place next to the rest of your configuration, and pass them on every open. Ditto applies them before it starts, so parameters that Ditto reads only at startup also take effect. Use ALTER SYSTEM SET only to change a value while the app runs, and SHOW to check a value. On SDK 5.1, whose DittoConfig has no system parameters, run ALTER SYSTEM SET every time you open Ditto, before you start sync, run queries, or register observers.

Why this matters

System parameters are kept in memory only, however you set them. After an app restart, or after Ditto is closed and reopened, every parameter is back at its default, so settings such as DQL_STRICT_MODE, USER_COLLECTION_SYNC_SCOPES, and TOMBSTONE_TTL_HOURS silently revert. Sync scopes applied after sync has started can let data sync unintentionally. In the configuration, a misspelled name or a value of the wrong type makes opening Ditto fail, so the mistake shows up at startup. With ALTER SYSTEM after open, parameters that Ditto reads only at startup, such as METRICS_EXPORTER_VIRTUAL_COLLECTION_ENABLED, are stored but have no effect.

What this means

ditto.sync.start() fails if a prerequisite (the expiration handler or the offline license token) is missing, and does nothing if sync is already active (ditto.sync.isActive). Keep Ditto open while the app is in the background; do not close it. If your app must not sync in the background, stop sync when the app moves to the background, and when it returns, restart only the sync that you stopped. In Flutter, start() and stop() return void, so do not await them (awaiting them is a compile error in Dart).

Why this matters

Closing cannot be undone: every later call on that instance fails, so you would have to open a new instance and register every subscription and observer again. Stopping sync has no such cost: the local store stays fully usable.

What this means

Change transports with ditto.updateTransportConfig, which starts from the current configuration, and change only what you need, for example all peer-to-peer transports at once or one transport under peerToPeer. Never assign a new, empty transport configuration. Treat global.syncGroup as an optimization, not as a security boundary. If more than six devices connect to a hub over TCP, raise MESH_CHOOSER_MAX_WLAN_CONNECTIONS on the hub so that it is in effect before sync starts: pass it in the system parameters of DittoConfig (SDK 5.2+), or on SDK 5.1 run ALTER SYSTEM SET after every open. Check how many clients your hub admits, and confirm the setting with Ditto support before you rely on it in production.

Why this matters

A hand-built configuration can silently stop devices from finding each other. A new transport configuration has every transport disabled, including the peer-to-peer transports that a default instance enables. Changes are applied asynchronously, and invalid values do not fail. In our testing with SDK 5.1.0 and 5.2.0, a device accepted 6 TCP connections by default. Additional clients of a hub received no data, no API reported an error, and only a WARN log line showed the problem. On 5.2.0, the default is still 6, and the connections that a device opened itself also count when it decides whether to accept another one, so a hub that also connects to other devices admits fewer clients. Changes of connect.tcpServers and of the TCP listener take effect while sync runs, and a device that loses a TCP connection tries again after connect.retryInterval (5 seconds by default). A device that only sets connect.tcpServers also listens for TCP on all interfaces; bind listen.tcp to 127.0.0.1 where it must not accept connections. Connections that a hub accepted over WebSocket did not count toward its TCP limit in our testing (30 clients synced), but Ditto documents no limit for them.

What this means

Release each Ditto object when you no longer need it: store observers and sync subscriptions (cancel(), or close() in Kotlin), presence and transport-condition observers, and attachment fetchers. Before you close Ditto, await your own pending queries and transactions, and release your observers. Where a write must reach another device before Ditto closes (at logout or at the end of a shift), wait with a timeout until its commitID is confirmed in system:data_sync_info. Close Ditto only when the whole app no longer needs it. DittoSwift 5.1.0 and 5.2.0 have no close(): Ditto shuts down when the last strong reference to the instance is released, so keep that reference in one owner. On Flutter 5.2.0, avoid closing and reopening Ditto in one process: in our testing, a later Ditto.open() or close() stopped when subscription or transaction objects of the closed instance were garbage-collected. Each SDK can list what is still registered, such as the store's observers: check that their number does not keep growing as the user moves between screens. In Flutter, also cancel the StreamSubscriptions on the observers' changes streams before closing, and use the instance only from the isolate that opened it.

Why this matters

Ditto objects hold native resources, so do not rely on garbage collection to release them. Closing does not clean up for you. Whether it waits for your pending work differs by SDK: in our testing with SDK 5.1.0 and 5.2.0, Flutter's close() failed in-flight execute() calls with DittoClosedException (the writes were stored) and, while a transaction was open, stopped the isolate; JavaScript's and Kotlin's close() waited for them; and in Swift, the release waited for an open transaction, but on 5.2.0 most writes still in flight failed with useAfterCloseError. Neither closing nor sync.stop() waits for changes that are still being sent: in our testing with SDK 5.1.0 and 5.2.0, a 1 MB write made right before closing did not leave the device until it synced again. In Flutter, close() also does not end an await for loop over an observer's changes stream, cancel() no longer does anything once Ditto is closed, and close() resets DittoLogger.customLogCallback for the whole process.

What this means

Write a :name placeholder for every value and pass the value as an argument. This includes IDs, user input, dates, limits, and whole documents (INSERT INTO orders DOCUMENTS (:order)). Never build DQL strings with string interpolation or concatenation. Parameter names are case-sensitive.

Why this matters

Interpolated input can change what a statement does (DQL injection). DQL also interprets backslash escapes in string literals, so user text that contains \ or quotes can be altered or can break the statement. Parameters keep their exact value and type. And because the statement text stays the same, Ditto can reuse the prepared plan from its statement cache.

Best-practices guide: Parameters and Literals, Executing DQL in Flutter, Executing DQL in JavaScript, Executing DQL in Kotlin, Executing DQL in Swift

Code example (sql) 
-- ✅ GOOD: Values travel as typed parameters
-- Arguments: {"customerId": "c-1", "pageSize": 50}
SELECT * FROM orders WHERE customerId = :customerId
ORDER BY createdAt DESC LIMIT :pageSize

-- ❌ BAD: The value was pasted into the statement text. Input such as
-- x' OR '1' = '1 turns the filter into one that matches every order.
SELECT * FROM orders WHERE customerId = 'x' OR '1' = '1'
What this means

To match any value in a list, pass the list as an array parameter without parentheses: WHERE status IN :statuses. To test whether an array field contains a value, use :tag IN tags or array_contains(tags, :tag).

  • Do not write IN (:statuses): the parentheses wrap the array in a one-element list, so nothing matches
  • Do not filter with ANY or EVERY ... SATISFIES ... END over a parameter or literal array in WHERE. For example, ANY s IN :statuses SATISFIES s = status END returns no rows in SDK 5.1.0 and 5.2.0; use status IN :statuses instead
  • Do not pass a single value where the statement expects an array: in our testing with SDK 5.1.0 and 5.2.0, status IN :statuses with a string instead of a list matched nothing
Why this matters

These mistakes return an empty result without an error, so the bug looks like missing data. status IN :statuses can also use an index on status.

-- ✅ GOOD: Membership against an array parameter

-- ❌ BAD: The array becomes a single list element, so no document matches

What this means

When you write an object literal inside a DQL statement, quote every key, for example {'status': 'open'}. Better still, avoid inline objects and pass documents as parameters (DOCUMENTS (:order)).

Why this matters

INSERT rejects unquoted keys. SELECT accepts them without an error but evaluates them as field references, which usually produces an empty object ({}).

Choose names that are not DQL keywords, such as orders, tasks, and createdAt. Never name a collection collection. If you cannot rename an existing reserved name, quote it with backticks in every statement. Do not start ordinary comments with /*+ or --+; those prefixes mark query directives.

Why this matters

SELECT * FROM collection fails with a parser error (expected identifier). A reserved name must be quoted with backticks in every statement that uses it.

What this means

A field can be absent from a document (MISSING) or present with the value null. A comparison involving either is neither true nor false, so WHERE does not return the row.

  • Filter optional booleans with coalesce(field, false) = false
  • Test existence with IS MISSING / IS NOT MISSING; IS NOT NULL is also true for a missing field
  • Remove a field with UNSET; writing null keeps the field present
Why this matters

Documents written by older app versions or other platforms often lack newer fields. A filter that ignores MISSING hides those documents without any error. Also, when no documents match, aggregates other than COUNT return MISSING, not 0.

What this means

Convert each row of a query result to plain values or to your own model type once, and then release the result or let it go out of scope. Read the rows only once, and keep the list of mutated document IDs instead of reading it again. In Kotlin, close the result, or read it inside the mapping function of execute.

Why this matters

Result and row objects reference native memory, which is released only when the result is released: by garbage collection in Flutter and JavaScript, by automatic reference counting in Swift, and with close() in Kotlin. Keeping them in state, in caches, or across observer callbacks keeps that memory alive. In Flutter, every pass over items also decodes the rows again.

What this means

Add RETURNING to an INSERT, UPDATE, DELETE, or EVICT statement to get the affected documents in its items. An UPDATE returns the documents after the change; DELETE and EVICT return them as they were before removal. Aggregates such as RETURNING COUNT(*) AS removed are allowed.

Why this matters

It replaces the "write, then query again" pattern, so the values you read are exactly the ones you wrote. For DELETE, you get the removed content from the same atomic statement. The commit ID and the mutated document IDs are populated as usual. Still, treat items as the result: when you need the IDs, include _id in the RETURNING list instead of relying on the mutated document IDs.

Best-practices guide: RETURNING (SDK 5.1+)

Code example (sql) 
-- ✅ GOOD: Update and read the new values in one statement
-- Arguments: {"ids": ["order-1"], "status": "shipped", "expected": "packed", "now": "2026-01-15T10:30:00.000Z"}
UPDATE orders SET status = :status, shippedAt = :now
WHERE _id IN :ids AND status = :expected
RETURNING _id, status, shippedAt
What this means

Watch for these common mistakes:

  • type(x) = 'number' never matches, because type() returns 'integer' or 'float'; use is_number(x)
  • date_add and date_sub return MISSING if you swap the part and count arguments; keep the order date_add(date, part, count). date_diff(date1, date2, part) returns date1 - date2, so swapping the dates flips the sign
  • GROUP BY and HAVING cannot reference projection aliases (the statement fails); repeat the expression
  • A comparison between values of different types evaluates to MISSING, even with = and != (1 = 'a', 1 != 'a', 1 < 'a')
Why this matters

Most of these look like valid queries, so the bug shows up as missing rows or fields in the UI rather than as an exception.

What this means

Write only the fields that changed, with UPDATE ... SET. When a user edits a document, write only the fields that the user changed. Do not read a document, change it in app code, and write the whole document back with ON ID CONFLICT DO UPDATE. For upserts and re-imports of data that another system owns, use ON ID CONFLICT DO UPDATE_LOCAL_DIFF. It skips fields whose values are unchanged, but it does not protect you from a stale in-memory copy: any old value that differs from the stored one is written back.

Why this matters

A whole-document rewrite can undo another device's edit. Ditto syncs changes field by field, so every field you write takes part in the merge, and an unchanged value written by this device can win against a real concurrent change from another device. Rewriting every field also makes each change larger. Even an UPDATE that writes the value that is already stored counts as a mutation and can trigger observers. In our testing with SDK 5.1.0 and 5.2.0, writing a field again with the value it already had replaced another device's earlier offline edit of that field.

Best-practices guide: Prefer field-level updates over whole-document rewrites, ON ID CONFLICT

Code example (sql) 
-- ❌ BAD: Read-modify-write of the whole document: read it, change status in
-- app code, and write every field back
-- Arguments: {"order": {"_id": "order-1", "customerId": "c-1", "status": "completed", "total": 42}}
INSERT INTO orders DOCUMENTS (:order) ON ID CONFLICT DO UPDATE

-- ✅ GOOD: Single field-level update that skips unchanged documents; the mutated
-- document IDs of the result tell whether anything changed
-- Arguments: {"id": "order-1", "status": "completed", "none": ""}
UPDATE orders SET status = :status
WHERE _id = :id AND coalesce(status, :none) != :status
What this means

Store line items, participants, or checklist entries as a map keyed by a stable ID ({"items": {"<itemId>": {...}}}), and keep any display order in a field such as position. When the user moves an entry, write only that entry's position, with a value between its new neighbors. Use arrays only for lists that one device owns or that are replaced as a whole. To add or update one entry from code, upsert a partial document with ON ID CONFLICT DO UPDATE_LOCAL_DIFF.

Why this matters

An array is a single register: when two devices change the same array concurrently, one version wins and the other change disappears without an error. Map entries merge independently, so concurrent additions and edits to different entries are all kept. In our testing with SDK 5.1.0 and 5.2.0, removing an entry with UNSET did not win over a concurrent edit of the same entry, and a partial entry remained. If one device may remove an entry while another edits it, mark the entry as removed instead (SET items.`<id>`.removed = true), and make readers skip entries whose required fields are missing or null. Renumbering every entry discards a reorder that another device makes at the same time (SDK 5.1.0 and 5.2.0).

Best-practices guide: Arrays and Maps

Code example (sql) 
-- ✅ GOOD: Add or update one line item of a map keyed by item ID. The key is
-- passed as data, never spliced into the statement. If the order does not
-- exist yet, this creates it.
-- Arguments: {"patch": {"_id": "order-1", "items": {"item-2": {"productId": "p2", "quantity": 1}}}}
INSERT INTO orders DOCUMENTS (:patch) ON ID CONFLICT DO UPDATE_LOCAL_DIFF
What this means

With the default settings, an object is a CRDT map. SET obj = {...} and ON ID CONFLICT DO UPDATE merge the new keys into the existing object: keys you leave out remain, and SET obj = {} changes nothing. Update nested fields individually (SET address.city = :city) and remove keys with UNSET address.zip. To replace an object as a whole, run UNSET and then SET in one transaction, or declare the field as REGISTER. Only a REGISTER guarantees that concurrent edits never mix two versions.

Why this matters

Code that expects an assignment to replace an object leaves stale keys behind. Maps are add-wins so that offline edits from many devices merge without data loss; the trade-off is that removals must be explicit. A key that another device adds while you remove or replace the object stays, with the value null (SDK 5.1.0 and 5.2.0), so code that reads such objects must handle null values.

-- ✅ GOOD: Replace an object: remove the old map, then write the new one, as two
-- statements in one transaction so that no observer sees the object missing
-- Arguments: {"id": "c-1"}
UPDATE customers UNSET address WHERE _id = :id

-- Arguments: {"id": "c-1", "address": {"street": "Main St", "city": "Oslo"}}

What this means

Change counters with APPLY f INCREMENT BY n (a negative n decrements). For an occasional correction, use APPLY f RESTART WITH n, and only while every device that changes the counter is in sync. Declare the counter in every statement, including the INSERT that sets the initial value, for example UPDATE COLLECTION inventory (stockCount COUNTER) .... Counters hold integers only, so count money in minor units. Create a counter document that every device creates on its own with INITIAL DOCUMENTS, and leave counter fields out of documents that you upsert or re-import.

  • Do not use counters for unique sequence numbers or for balances that must never go below zero
  • Do not use counters for values you can compute with COUNT(*)
Why this matters

When two devices run SET stock = stock - 1 concurrently, one of the decrements is lost, even while both are online: in our testing with SDK 5.1.0 and 5.2.0, six connected devices that each added 1 a hundred times kept only 101 to 129 of 600 increments. Counters (COUNTER, and the legacy PN_COUNTER) are the only CRDT types that add concurrent changes together. An undeclared INSERT stores the initial value as a register, so a later increment starts a separate counter at 0. A RESTART discards every increment that the restarting device has not received yet, including increments that other devices make later while offline (SDK 5.1.0 and 5.2.0). An upsert or a plain INSERT that writes a counter value restarts the counter in the same way.

Best-practices guide: Counters, Writing documents that contain counters

Code example (sql) 
-- ❌ BAD: Read-modify-write on a register. Two devices that sell an item
-- concurrently both write the same value; one decrement is lost.
-- Arguments: {"id": "item-1"}
UPDATE inventory SET stockLevel = stockLevel - 1 WHERE _id = :id

-- ✅ GOOD: Concurrent decrements are combined.
-- Arguments: {"id": "item-1"}
UPDATE COLLECTION inventory (stockCount COUNTER)
APPLY stockCount INCREMENT BY -1
WHERE _id = :id
What this means

Use UUIDs (version 4) from your platform's UUID generator, composite IDs that combine stable scope fields with a UUID ({"storeId": "s1", "orderId": "<uuid>"}), or let Ditto generate the ID. Never use sequential numbers or timestamp-only IDs. Keep human-readable numbers such as "#A-0042" in a separate field, and put only immutable attributes into _id. Use one type for the IDs of a collection, and normalize IDs built from user input (one Unicode form, one letter case).

Why this matters

Offline devices cannot coordinate a sequence, so two of them can create the same ID. After sync, the two documents become one document with their fields mixed together. _id cannot be changed after creation, so keep attributes that may change out of it. IDs compare by type and exact value: 1 and '1', or the same name in two Unicode forms, identify different documents.

What this means

Ditto logs a warning for documents above 256 KiB (soft limit) and rejects INSERT and UPDATE statements that would make a document larger than 5 MiB (hard limit). Store binary content as attachments, move data that grows without bound (history, readings, comments) into its own collection, and leave both limits at their defaults. On SDK 5.2+, include system:sync_degradations in your diagnostics.

Why this matters

Large documents cost storage and memory on every device, make merges more expensive, and slow down initial replication: over Bluetooth LE, a 256 KiB document takes more than 10 seconds to replicate the first time. A write that exceeds the hard limit fails with the SDK's error, whose message contains exceeds limit of ... bytes; handle it at the call site that may produce it. The limit is checked only for local writes, so offline additions on two devices can merge into a document above it. After that, every UPDATE of the document fails on every device (SDK 5.1.0). A device on 5.2.0 instead drops a change that would push a document over its hard limit and lists the document in system:sync_degradations. In our testing, the devices then kept different versions of the document without any error, and updates of it stopped in both directions. What this means

Use DELETE only when both of these hold: no other device updates the same document concurrently, and every device connects within the tombstone TTL (TOMBSTONE_TTL_HOURS, 7 days by default on Small Peers). A device that stays offline longer than the TTL can resurrect deleted data (zombie data). A Small Peer tombstone TTL above the Ditto Server tombstone TTL makes tombstones sync back to the server again and again.

What this means

Create the indexes your queries need on every device, after opening Ditto and before any query or observer runs. Skip this step where the store is in memory, which does not support indexes (Flutter Web and the JavaScript SDK in browsers). IF NOT EXISTS checks only the index name, so to change a definition, create the index under a new name. Why this matters

Why this matters

Code example (sql)

What this means

Compare indexed fields directly, and apply functions to the value, not to the field:

  • Do not wrap an indexed field in a function, as in lower(name) = :name
  • Make sure every branch of an OR can use an index
  • Use LIKE 'abc%' instead of starts_with()
  • Match the key order and sort direction of a composite index, and index the full path you filter on, such as address.city
  • Keep each field's CRDT type declaration consistent, and do not index fields that are written with more than one type
Why this matters

The planner picks indexes by rules, not by statistics. A function on the field, an OR branch without an index, or starts_with() makes the query fall back to a collection scan. According to Ditto's documentation, an indexed field written with mixed CRDT type declarations can produce incorrect or mis-ordered results.
