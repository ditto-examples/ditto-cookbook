# Ditto Transports and Presence Reference

Transport configuration, TCP hubs, known peers, transport diagnostics, multicast, and presence for Ditto SDK 5.2.0, for every SDK. Copied from `§ Transport Configuration`, `§ Presence`, and `§ Recording presence in documents` in `../../guide/reference/best-practices/setup-and-lifecycle.md`; the code for each SDK is in the *Transports and Presence in <SDK>* section of its page.

## Transport Configuration

**Change transports by updating the current transport configuration; never replace it with a new, empty one, which disables every transport.** A new Ditto instance enables the peer-to-peer transports of its platform: in testing with SDK 5.1.0 and 5.2.0, Bluetooth LE, LAN, and AWDL on macOS and iOS (also with the JavaScript SDK on Node.js on macOS), and Bluetooth LE, LAN, and Wi-Fi Aware on Android; Wi-Fi Aware stayed disabled on macOS although Ditto's documentation says that all peer-to-peer transports are enabled (`§ A new instance enables the platform's peer-to-peer transports, and an empty configuration enables none`). When you connect to Ditto Server, the Server URL is used automatically; you do not need to add it to the transport configuration.

The transport configuration has the same structure in every SDK: `peerToPeer` (Bluetooth LE, LAN, AWDL, Wi-Fi Aware), `connect` (TCP servers, WebSocket URLs, and the retry interval; the field names follow each SDK's conventions, for example `webSocketUrls` in Flutter and `websocketURLs` in JavaScript), `listen` (`tcp`, `http`), and `global`. Each SDK offers an update call that starts from the current configuration (`updateTransportConfig`; see [Transports and Presence in Flutter](../../guide/reference/best-practices/platforms/flutter.md#transports-and-presence-in-flutter), [JavaScript](../../guide/reference/best-practices/platforms/javascript.md#transports-and-presence-in-javascript), [Kotlin](../../guide/reference/best-practices/platforms/kotlin.md#transports-and-presence-in-kotlin), and [Swift](../../guide/reference/best-practices/platforms/swift.md#transports-and-presence-in-swift)).

**✅ DO:**
- Update the current configuration and change only the settings you need.
- Enable or disable all peer-to-peer transports at once, or individual transports through `peerToPeer`.
- Observe transport conditions to detect missing permissions or disabled radios.
- Configure each TCP link in one direction only: the hub listens, and the clients list the hub in `connect.tcpServers`.
- On a hub that more than six devices connect to over TCP, raise the TCP connection limit on the hub so that it is in effect before sync starts (see the note below).

**❌ DON'T:**
- Build a new transport configuration from scratch and assign it: a new configuration has **every transport disabled**, including the peer-to-peer transports that a default instance enables (in testing with every SDK on SDK 5.1.0 and 5.2.0).
- Use `MESH_CHOOSER_AT_CAPACITY_ACTION` to admit more TCP clients than the limit; the hub keeps replacing connections (see the note below).
- Treat `global.syncGroup` as a security boundary. It is an optimization only: in our testing, devices in different sync groups still synced when they were connected explicitly (see [Relay, rewrite, and subscription behavior held on SDK 5.1.0 and 5.2.0](../../guide/reference/knowledge/observations/subscriptions-and-replication.md#relay-rewrite-and-subscription-behavior-held-on-sdk-510-and-520)).

> **Note (SDK 5.1.0 and 5.2.0):** A device accepts a limited number of connections per transport. For TCP, the limit is 6 by default (system parameter `MESH_CHOOSER_MAX_WLAN_CONNECTIONS`). In our testing with a TCP hub and eight clients, the hub accepted six, and the remaining two received no data at all; no API reported this, and only the log showed a `WARN` line, `failed to connect to peer error=... at capacity for this transport` (see [A device accepts six TCP connections by default](../../guide/reference/knowledge/observations/connections-and-presence.md#a-device-accepts-six-tcp-connections-by-default)).
>
> On 5.2.0, a device also counts the connections that it opened itself when it decides whether to accept another one (the 5.2.0 release notes describe this as counting accepted and outgoing LAN connections together). In our testing, a hub that also connected to two other devices dropped two of its six clients on 5.2.0, and a relay that connected to an upstream hub accepted only five clients (see [SDK 5.2.0 counts outgoing connections toward the TCP limit](../../guide/reference/knowledge/observations/connections-and-presence.md#sdk-520-counts-outgoing-connections-toward-the-tcp-limit)). Outgoing connections themselves are not limited (see [Outgoing TCP connections are not limited](../../guide/reference/knowledge/observations/connections-and-presence.md#outgoing-tcp-connections-are-not-limited)), and the default is still 6.
>
> A client that the hub did not accept appears in no device's presence graph, so presence shows correctly that it is not connected (see [The presence graph includes indirect peers and all of their connections](../../guide/reference/knowledge/observations/connections-and-presence.md#the-presence-graph-includes-indirect-peers-and-all-of-their-connections)). Two devices that listed each other in `connect.tcpServers` kept two TCP connections. When every device lists every other device, a device on 5.2.0 kept 3 to 7 direct connections (6 to 9 TCP connections), so a mesh of seven or more devices was not fully connected, although every device still listed all the others in `remotePeers` and changes reached every device within 24 to 80 ms through the others; on 5.1.0, devices kept up to 15 TCP connections, many of them duplicates (in our testing; see [On SDK 5.2.0, devices in a full TCP mesh of seven or more keep 3 to 7 direct connections](../../guide/reference/knowledge/observations/connections-and-presence.md#on-sdk-520-devices-in-a-full-tcp-mesh-of-seven-or-more-keep-3-to-7-direct-connections)). Count devices with `remotePeers`, not with direct connections.
>
> `MESH_CHOOSER_AT_CAPACITY_ACTION` decides what a full hub does when another client arrives. It takes an integer (a string such as `'DropOldest'` is rejected), and with the default, 0, the extra client never connected. According to the 5.2.0 release notes, the settings that drop the oldest or the newest peer wait until the new peer has finished connecting. In our testing with the values 1 and 2, every client received data, but the hub kept replacing connections in a 5-second cycle, and at every check, at least one client was not connected (on 5.2.0, and on 5.1.0 with 2; on 5.1.0 with 1, the cycle stopped in some runs; see [At-capacity actions 1 and 2 admit extra clients but keep replacing connections](../../guide/reference/knowledge/observations/connections-and-presence.md#at-capacity-actions-1-and-2-admit-extra-clients-but-keep-replacing-connections)). Raise `MESH_CHOOSER_MAX_WLAN_CONNECTIONS` instead.
>
> If more than six devices connect to one hub, raise the limit **on the hub** so that it is in effect **before** sync starts: pass it in the system parameters of `DittoConfig` (SDK 5.2+), or on SDK 5.1 run `ALTER SYSTEM` after opening Ditto and before you start sync. In our testing, raising it after sync had started did not admit the rejected clients, even after 60 seconds (see [Raising the TCP limit takes effect only before sync starts](../../guide/reference/knowledge/observations/connections-and-presence.md#raising-the-tcp-limit-takes-effect-only-before-sync-starts)).

> **Note (SDK 5.1.0 and 5.2.0):** A device that only connects over TCP also accepts connections. In our testing with the JavaScript SDK on macOS, a device with only `connect.tcpServers` set listened for TCP on all interfaces at a free port, and another device could connect to it and sync (see [A device that only connects over TCP also listens for TCP connections](../../guide/reference/knowledge/observations/connections-and-presence.md#a-device-that-only-connects-over-tcp-also-listens-for-tcp-connections)). To accept no TCP connections from other devices, enable `listen.tcp` with `interfaceIP` set to `127.0.0.1` (`port` 0 picks a free port). Only devices with the same Database ID and valid credentials can sync, so this matters most for small-peers-only deployments without a shared key and for network reviews.

**Hub load**: the CPU that a hub spends on each change grows with the number of devices connected to it, even when no other device subscribes to the changed document. In our testing on a 14-core Mac, one change cost the hub at most about 6 ms of CPU with one client and about 40 ms with 30 clients, and 30 clients that each wrote 5 times a second used about 2.6 cores (see [Hub CPU per change grows with the number of connected devices](../../guide/reference/knowledge/observations/performance-measurements.md#hub-cpu-per-change-grows-with-the-number-of-connected-devices)). Before you use a mobile device as a hub, estimate the number of clients and how often they write, and write frequently changing values (positions, sensor readings) less often or in batches.

**Replacing a hub**: a new, empty hub device recovers the data from its clients, including their tombstones, so deleted documents stay deleted (until the tombstones are reaped, see [Tombstone TTL and reaping](../../guide/reference/best-practices/deletion-and-storage.md#tombstone-ttl-and-reaping)). Documents that only the old hub held are not recovered (in our testing; see [A new, empty hub recovers the data from its clients](../../guide/reference/knowledge/observations/subscriptions-and-replication.md#a-new-empty-hub-recovers-the-data-from-its-clients)). Back up data that only the hub writes, or let a client subscribe to it.

Changes of `connect.tcpServers` and of the TCP listener take effect while sync is running, without stopping and starting sync: in our testing, a device connected or disconnected within about 50 to 150 ms (see [TCP targets and listeners change while sync runs](../../guide/reference/knowledge/observations/connections-and-presence.md#tcp-targets-and-listeners-change-while-sync-runs)). System parameters such as `MESH_CHOOSER_MAX_WLAN_CONNECTIONS` are different: raising the limit after sync had started had no effect.

A device that loses a TCP connection, or fails to connect, tries again after `connect.retryInterval` (5 seconds by default in every SDK; see [A denied peer retries at the retry interval](../../guide/reference/knowledge/observations/connections-and-presence.md#a-denied-peer-retries-at-the-retry-interval)): in our testing, clients reconnected to a restarted hub about 4 seconds after it was open again with the default, and about 1.1 seconds with an interval of 1 second (see [A lost TCP connection is retried at the retry interval](../../guide/reference/knowledge/observations/connections-and-presence.md#a-lost-tcp-connection-is-retried-at-the-retry-interval)). A shorter interval suits devices that must stay connected to a hub, such as the terminals of a store.

Configuration changes are applied asynchronously while sync is running, and invalid values do not fail: an invalid `connect.tcpServers` entry or listen address only produces a log line (for example `Failed to start TCP server error=Bind address could not be parsed`). You can also point devices at a known peer with the `TRANSPORTS_DISCOVERED_PEERS` system parameter, which can be set before or after sync starts and is validated (`type` is optional and must be `'force'` or `'candidate'`). It works only while the LAN transport (`peerToPeer.lan`) is enabled on the device that sets it, which is the default; with peer-to-peer transports disabled, the value is stored but nothing connects, so use `connect.tcpServers` instead. Like every system parameter, it is not persisted: pass a fixed address in the system parameters of `DittoConfig` (SDK 5.2+), or set it with `ALTER SYSTEM` after each open, for example when the address is discovered at run time:

```sql
ALTER SYSTEM SET TRANSPORTS_DISCOVERED_PEERS = [{'address': 'tcp://192.168.1.10:4040', 'type': 'force'}]
```

**WebSocket sync between Small Peers** (accepting WebSocket connections on the HTTP listener) is **off by default** (`listen.http.websocketSync = false`). Enable it only when you need it and configure TLS (`tlsKeyPath` and `tlsCertificatePath`); without them the listener uses plain HTTP.

Connections that a hub accepts over WebSocket do not count toward its TCP limit. In our testing with SDK 5.0.3, 5.1.0, and 5.2.0, a Small Peer hub that accepted WebSocket connections synced with all of 30 clients, while over TCP it served six, and with its TCP limit lowered to 2, it still served 8 WebSocket clients next to 2 TCP clients (see [WebSocket connections to a Small Peer hub do not count toward the TCP limit](../../guide/reference/knowledge/observations/connections-and-presence.md#websocket-connections-to-a-small-peer-hub-do-not-count-toward-the-tcp-limit)). This is an alternative to raising `MESH_CHOOSER_MAX_WLAN_CONNECTIONS` for hubs with more clients, with limits of its own: Ditto does not document a limit for WebSocket connections, we tested at most 30 clients on one machine without TLS, and a WebSocket connection that stops responding takes about 15 seconds to be dropped, against about 7 for TCP (see [Key Characteristics](../../guide/reference/knowledge/understanding-ditto.md#key-characteristics) and [Each device sends over one of two connections and waits when it stalls](../../guide/reference/knowledge/observations/connections-and-presence.md#each-device-sends-over-one-of-two-connections-and-waits-when-it-stalls)). Test the number of devices you plan before you rely on it.

### Diagnosing transport problems (SDK 5.1+)

Because configuration changes do not fail, observing the transport conditions is the way to see why a transport is not working: missing Bluetooth permissions, Bluetooth or Wi-Fi turned off, no BLE hardware, the app being in the background, mDNS or TCP listen failures, and so on. Stop the observer when you no longer need it. On Android, the SDK also reports which runtime permissions Ditto needs and which are missing; request them before you start sync. Since SDK 5.2, the list of required permissions covers only the generally available transports; the permissions for multicast are returned separately (see [Multicast (Beta) (SDK 5.1+)](../../guide/reference/best-practices/setup-and-lifecycle.md#multicast-beta-sdk-51)).

### Multicast (Beta) (SDK 5.1+)

Multicast is an opt-in transport that sends each update once to a multicast group instead of once per connection, which reduces connection overhead in dense deployments. It is a private beta feature: **use it only in coordination with Ditto support**. It is configured through `peerToPeer.multicastBeta` and requires additional platform entitlements and permissions (for example the multicast entitlement on iOS and `CHANGE_WIFI_MULTICAST_STATE` on Android). It is not available on the Web or on Windows, and changes made while sync is active take effect only after sync is stopped and started again. On Android with SDK 5.2+, the multicast permissions are no longer part of the list of required permissions; request them separately.


## Presence

`ditto.presence` shows which peers this device can see and how it is connected to them, which is useful for connection indicators and diagnostics.

- Observing presence returns an observer. The callback is called with the current graph shortly after you start observing (asynchronously), and again whenever peers appear, disappear, or change their connections. Stop the observer when you no longer need it.
- Updates are batched: in our testing, callbacks arrived about once per second, also while many peers kept coming and going, so a change reached the callback within about 1 second and one callback can cover several changes (see [Presence reports a joining peer after about 1.2 seconds](../../guide/reference/knowledge/observations/connections-and-presence.md#presence-reports-a-joining-peer-after-about-12-seconds) and [Presence callbacks stay at about one per second while peers come and go](../../guide/reference/knowledge/observations/connections-and-presence.md#presence-callbacks-stay-at-about-one-per-second-while-peers-come-and-go)). Show a connection state only after it has held for a few seconds, not the raw count of `remotePeers`, which swings while peers come and go. The callback is also called with an unchanged graph, so compare the graph with the previous one before you update the UI.
- The graph's `localPeer` describes this device, and `remotePeers` lists the other known peers, including peers that are reachable only through other peers. Each peer has a peer key, a device name, whether it is connected to Ditto Server, its connections, and its peer metadata. To tell direct neighbors apart, check whether one of a peer's connections has this device's peer key at one of its ends: a remote peer's connections list all of that peer's connections, not only the one to this device. The connection type has no TCP value; TCP connections, including those to a hub, are reported as `accessPoint` (in our testing with the JavaScript SDK; see [The presence graph includes indirect peers and all of their connections](../../guide/reference/knowledge/observations/connections-and-presence.md#the-presence-graph-includes-indirect-peers-and-all-of-their-connections)).
- `presence.graph` returns the current graph once, without observing.
- A peer that stops responding without closing its connection stays in the graph for several seconds: in our testing over TCP, about 7 seconds after the network went silent, while a shorter outage was not noticed at all, and about 9 seconds for a suspended process; a process that ended disappeared at once (see [A silent network outage removes a peer after about 7 seconds](../../guide/reference/knowledge/observations/connections-and-presence.md#a-silent-network-outage-removes-a-peer-after-about-7-seconds) and [A suspended device leaves the presence graph after about 9 seconds](../../guide/reference/knowledge/observations/connections-and-presence.md#a-suspended-device-leaves-the-presence-graph-after-about-9-seconds)). Other transports, such as Bluetooth LE, may take a different time; expect a connection indicator to lag by this much.
- A peer in the graph is not necessarily up to date: over a slow link, a peer that was transferring a large attachment stayed in the graph while other changes waited behind the transfer (see [Slow links keep the connection and the presence entry](../../guide/reference/knowledge/observations/connections-and-presence.md#slow-links-keep-the-connection-and-the-presence-entry)). Two connections to a peer in the graph do not mean that sync continues when one of them stalls (see [Each device sends over one of two connections and waits when it stalls](../../guide/reference/knowledge/observations/connections-and-presence.md#each-device-sends-over-one-of-two-connections-and-waits-when-it-stalls)).
- `presence.peerMetadata` sets metadata for this device (a JSON object of at most 4096 bytes when encoded; larger values fail). It reaches every peer in the mesh, but a peer that has just appeared can show empty metadata until its metadata arrives. Setting it again replaces the whole object; keys are not merged. Changes reach other peers about once per second, as the value current at that moment, so intermediate values are skipped (in our testing; see [Peer metadata changes reach other peers about once per second](../../guide/reference/knowledge/observations/connections-and-presence.md#peer-metadata-changes-reach-other-peers-about-once-per-second)).
- `ditto.deviceName` is the name that other peers see as the peer's device name. Its default depends on the SDK: according to the API references, Flutter derives it from the device model and JavaScript from the host name (on Node.js, it was the host name). Names longer than 24 bytes are truncated, in Flutter when you set them and in JavaScript when sync starts. Set it before you start sync: in our testing, a change made while sync was running did not reach other peers until sync was stopped and started again (see [Peer metadata is replaced, not merged, and the device name is read when sync starts](../../guide/reference/knowledge/observations/connections-and-presence.md#peer-metadata-is-replaced-not-merged-and-the-device-name-is-read-when-sync-starts)). Other peers also see each peer's `os` and `dittoSdkVersion`, which helps to find devices that run an older SDK (see [Presence shows each peer's SDK version](../../guide/reference/knowledge/observations/connections-and-presence.md#presence-shows-each-peers-sdk-version)).

**✅ DO:**
- Stop presence observers when the screen or feature that uses them goes away.
- Keep peer metadata small and non-sensitive, such as a role or a display name. Every connected device receives about twice its size whenever a device joins or changes it: in our testing over TCP, 3 KB of metadata cost each device about 6 KiB per change (see [Presence traffic carries each peer's metadata, and idle traffic grows faster than the number of devices](../../guide/reference/knowledge/observations/connections-and-presence.md#presence-traffic-carries-each-peers-metadata-and-idle-traffic-grows-faster-than-the-number-of-devices)). Write large or frequently changing values (positions, task state) to documents instead.
- Set peer metadata once at startup (for example `{"role": "cashier"}`), not from individual screens. Other peers see at most about one change per second.
- Set the device name to a name that identifies the device for your support staff and not a person, before you start sync.

**❌ DON'T:**
- Put secrets, tokens, or personal data in peer metadata. Peer metadata, and the `identityServiceMetadata` returned by your authentication webhook, are shared with every peer in the mesh, not only with directly connected peers.

### Recording presence in documents

Presence describes the mesh only as it is now. An app that needs to know later which peers were around, such as a device inventory, a last-seen list, or a record of which devices met, writes what presence reports to a collection, and those writes sync like any other data. What the record must answer, how precisely, for how long, and which devices read it differ from app to app. The rules below apply to every such design; review one by asking what triggers each write, how many devices write the same document, how many documents the collection can hold, and which devices receive them.

What a record of presence can show:

- **The peers that the recording devices could reach, not every device at a site.** The graph includes peers that are reachable only through other peers, so a peer in it is not necessarily nearby. It leaves out devices whose sync is stopped, that a hub did not accept, or that are in another part of the mesh (see [The presence graph includes indirect peers and all of their connections](../../guide/reference/knowledge/observations/connections-and-presence.md#the-presence-graph-includes-indirect-peers-and-all-of-their-connections)). A record that several devices write is the union of what each of them could reach.
- **Times accurate to seconds.** A joining peer appears after about 1.2 seconds, and a peer that stops responding stays for about 7 to 9 seconds (see [Presence](#presence)).
- **Persistence directories, not devices.** The peer key belongs to the persistence directory: a device whose directory is deleted, for example by a reinstall or by clearing the app's data, comes back with a new peer key (see [Deleting the directory after close() leaves no data behind](../../guide/reference/knowledge/observations/persistence-directory.md#deleting-the-directory-after-close-leaves-no-data-behind)), and a record keyed by peer key gains an entry. Device names are not unique either.

**Write at the pace that the record needs, not at the pace of presence callbacks.** Presence calls back about once per second while peers come and go and about every 15 seconds while nothing changes, and every device lists every peer that it can reach. When each of N devices writes every peer on every callback, they write about N × (N − 1) documents each time the graph changes, and each write syncs to every device that subscribes, whether or not the time moved enough to matter. In our testing with SDK 5.1.0 and 5.2.0, four devices that did so wrote 215 to 245 documents in about 80 seconds, which called the store observers of the four devices 278 to 364 times; with a 20-second threshold and a timer with a random interval, they wrote 12 to 16 documents (see [Writing every remote peer on every presence callback multiplies the writes by the number of devices](../../guide/reference/knowledge/observations/connections-and-presence.md#writing-every-remote-peer-on-every-presence-callback-multiplies-the-writes-by-the-number-of-devices)). Over a link limited to 10 KB/s, twelve devices that wrote every peer on every callback took 53 to 61 percent of the link while a client came and went, and delayed other documents on that link from under 50 ms to 123 to 333 ms at the median; with the timer and threshold, the delays stayed as without the record (see [Presence written on every callback delayed other documents on a slow link](../../guide/reference/knowledge/observations/connections-and-presence.md#presence-written-on-every-callback-delayed-other-documents-on-a-slow-link)).

**✅ DO:**
- Choose the precision that the record needs, such as "last seen within 5 minutes", and write a peer only when its recorded time is older than that. Keep what presence reports in memory, and let a trigger whose rate you choose write, such as a timer, not every presence callback.
- Where several devices write the same peer, keep them from writing it at the same moment, for example with a timer whose offset or interval is random on each device. A change of the graph reaches every device within about a second, and timers that start together fire together, so devices that write then all write before any of them has received the others' writes. In our testing, writing from the presence callback with the same check, or from a timer that started on every device at the same moment, still wrote each peer from several devices within 1 second; a timer with a random interval did not (see [Writing every remote peer on every presence callback multiplies the writes by the number of devices](../../guide/reference/knowledge/observations/connections-and-presence.md#writing-every-remote-peer-on-every-presence-callback-multiplies-the-writes-by-the-number-of-devices)).
- Write the peers that are due in one transaction. Other devices' observers receive the transaction in one callback (see [Remote changes arrive in a few callbacks, and a transaction in one](../../guide/reference/knowledge/observations/observer-behavior.md#remote-changes-arrive-in-a-few-callbacks-and-a-transaction-in-one)).
- Let recording devices that subscribe to the record skip peers that another device recorded recently enough. Read the recorded times with a store observer that only updates memory. A recording device that does not subscribe cannot see the other devices' writes, so each such device writes every peer itself. The check compares times from different device clocks, so a device whose clock runs ahead can make the others skip a peer until real time catches up.
- Decide which devices record. Every device recording every peer keeps the record complete when the mesh splits, at the highest cost. Devices of one role, such as a fixed hub, cost less but see only their part of the mesh. Each device recording only itself, as a heartbeat, has one writer per document and costs one write per device and interval, but it records that the device was running and could sync, not which devices could reach it.
- Bound the number of documents. Give each peer one document, or one per peer and period, with an `_id` derived from the peer key (and the period), so that every recording device writes the same document. Do not insert a new document for every sighting. Keep the record for a limited time with a period field that does not change, a subscription to recent periods with a boundary passed as an argument, and an eviction of older ones (see [Time-based eviction](../../guide/reference/best-practices/deletion-and-storage.md#time-based-eviction)). A last-seen time changes with every write, so a subscription that filters on it does not suit (see [Scope Balancing](../../guide/reference/best-practices/sync-and-subscriptions.md#scope-balancing)).
- Subscribe to the record only on the devices that read it, and on the devices that relay it to them (see [Multi-hop relay](../../guide/reference/best-practices/sync-and-subscriptions.md#multi-hop-relay)). Every other device then receives none of these writes.
- Store times with one fixed-precision UTC helper (see [Timestamps](../../guide/reference/best-practices/data-modeling.md#timestamps)).
- Keep the presence callback and the store observer short, and update the screen from the record as from any observer (see [Keep observer callbacks fast](../../guide/reference/best-practices/observers.md#keep-observer-callbacks-fast) and [Backpressure (SDK 5.1+)](../../guide/reference/best-practices/observers.md#backpressure-sdk-51)).

**❌ DON'T:**
- Write every remote peer from every presence callback.
- Write the record from the store observer that reads it. The recorded time depends on the device and its clock, so devices that write it in reaction to each other's writes keep overwriting each other (see [Writing from Observers](../../guide/reference/best-practices/observers.md#writing-from-observers)).
- Expect one last-seen field to hold the latest time. The field is a register, and the write made later by the clock wins, not the larger time: a device that has not yet received a newer time and writes an older one moves the time back, also when both devices' clocks agree. In our testing, an older time written 50 ms after a newer one replaced it on both devices. Where the time must never move back, let each recording device write under its own key, such as `seenBy.<recorder>`, and take the latest when you read, at the cost of one entry per recorder in each document (see [An older time written later replaces a newer one, while a key per writer keeps both](../../guide/reference/knowledge/observations/merge-behavior.md#an-older-time-written-later-replaces-a-newer-one-while-a-key-per-writer-keeps-both)).

```sql
-- ✅ GOOD: One possible model. A recording device writes the peers that are
-- due, all in one transaction. One document per peer and day: every recording
-- device writes the same document, and old days are evicted by their day field.
-- DO UPDATE_LOCAL_DIFF skips the day field, which does not change.
```
